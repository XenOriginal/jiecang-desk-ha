# 03 · 系统架构与固件设计

> 固件：`源码快照/esphome/desk-c3.yaml` + `desk_proto.h`
> 环境：ESPHome 2026.10.2 / ESP-IDF 5.5.6 / `board: esp32-c3-devkitm-1`
> 占用：flash 49.6%，RAM 32.2%（321 KB 中约 103 KB）

## 2. 核心设计：零后台流量（事件驱动）

### 起因

手控器屏幕一直亮着。原因是旧固件每 900 ms 发一帧 `0x07` 请求设置 —— 手控器和控制盒挂在
**同一条总线**上，屏幕显示的高度就是这条总线送来的，所以**总线上任何一帧都会唤醒屏幕**，
900 ms 的节奏正好一直给它的待机计时器续命。

### 现在的策略

| 场景 | 行为 |
|---|---|
| 空闲 | **一帧不发** |
| 用户手动控器动桌子 | 它与盒子之间的报文从 RX 照收，直接解析 —— 这是天然的取数窗口 |
| 一次运动结束 | **补发一帧** `0x07` 对齐限位/记忆位（可用 `post_motion_sync: "false"` 关掉） |
| 开机 / OTA 后 | 最多一帧（可用 `boot_sync: "false"` 关掉） |

判定条件（`interval: 250ms` 里的状态机）：

```
post_sync = g_sync_armed                 // 刚停过一次，只消费一次
         && !moving                       // 高度 900ms 未变
         && now - g_last_move > 1200
         && now - g_last_rx   > 400       // 总线安静
         && now - g_last_tx  > 1200
```

因为 `g_sync_armed` 用一次就置回 `false`，所以它**永远不会退化成轮询**。

### 代价：安静之后的头一帧会丢

关掉轮询后立刻显形（这个现象在 PC 端早就记过，只是被 900 ms 的轮询掩盖了）：

| 现象 | 证据 |
|---|---|
| 空闲几分钟后按单步，第 1 次毫无反应 | 1079 → 1079 → 1090 → 1101（第 2、3 次才动） |
| 定点帧被收成残帧，桌子朝错误目标跑 | 目标 1120，实际从 1129 一路降到 1079 才停（**50 mm 过冲**） |

## 3. 预热帧（priming）

修法：**每次真正下命令前，先发一帧 `0x07` 把总线"敲醒"，70 ms 后再发真命令。**

`0x07` 只读不动作，最坏情况是什么都不发生；副作用只是手控器屏幕又亮一下，
而这一刻本来就已经被接下来的操作点亮了。

`desk_proto.h` 里三个 helper，语义不同，**不幂等的命令绝不能重发**：

| helper | 序列 | 用在哪 | 幂等 |
|---|---|---|---|
| `primed_simple(u, cmd)` | `07` → 70 ms → `cmd` | 单步、急停、存记忆位 | 单步**不可**重发（行程翻倍） |
| `primed_goto(u, mm)` | `07` → 70 ms → `1B` → 80 ms → `1B` | 定点 | ✅ 同目标重发安全 |
| `primed_read(u)` | `07` → 90 ms → `07` | 读状态 | ✅ 幂等 |

实测（`Rx Frames` 是诊断实体，空闲时必须不动）：

```
空闲 20s        frames 20 → 20                            ✓ 零流量
空闲后单发单步   1101 → 1111                                ✓ 第一帧不再丢
goto 1050       实测 1051，停稳后补抓校正为 1050             ✓ 无过冲
再空闲 15s      frames 67 → 67                             ✓ 回到静默
```

## 4. 帧解析实现要点

`interval: 25ms` 里做两件事：把 RX 字节灌进 `std::vector`（上限 96 字节），然后循环剥帧。

```cpp
if (buf[0] != 0xF2 || buf[1] != 0xF2) { buf.erase(buf.begin()); continue; }
const size_t len   = buf[3];
const size_t total = 6 + len;              // F2 F2 CMD LEN ... CHK 7E
if (buf.size() < total) break;             // 凑够再解析
uint8_t cs = 0;
for (size_t k = 2; k < 4 + len; k++) cs += buf[k];   // 只算 CMD+LEN+PARAMS
if (cs != buf[total-2] || buf[total-1] != 0x7E) { buf.erase(buf.begin()); continue; }
```

内建的坑（每一条都对应一次真实故障）：

| 坑 | 处理 |
|---|---|
| CHK 只算 `CMD+LEN+PARAMS`，不含 `F1 F1` | `checksum()` 只对 payload 求和 |
| `0x7E` 出现在载荷里 | 按 `LEN` 算帧长，不扫终止符 |
| 帧被拆成两次读到 | `vector` 累积，凑够 `6+LEN` 才解析 |
| 端口刚开/模块刚启动首帧可能丢 | `primed_*` 热身；MCU 侧实测无此现象，重发只是保险 |
| 刚停稳立刻发运动命令被忽略 | 状态机 1.2 s / 3 s 抑制窗口天然覆盖 |
| 上电瞬间 IO 不确定 | IO20/21 不参与 strapping；ROM 乱码会被盒子当坏帧丢弃 |
| UART 读取 API | 2026.x 用 `available()` + `read_byte()`；`read()` 只在 `UARTDevice` 包装类上 |
| `binary_sensor.template` 的 `update_interval` | 新版不支持，改在 `interval:` 里 `publish_state()` |

## 6. cover 映射（在 HA 侧，不在固件）

`cover.desk` 是 HA 模板，0% = 坐（851），100% = 站（1129）。

两个坑：

1. **不要设 `device_class`。** 设成 `shutter`/`curtain` 后前端整套文案变成"窗帘"，
   连按钮提示都是"打开窗帘/关闭窗帘"。改给 `icon: mdi:desk`，前端按普通 cover 处理。
2. **端点各内缩 1 mm。** 软限位报 850/1130，但 number 实体有效区间是 851–1129，
   直接拿 `soft_max` 当目标会报「1130 超出 851-1129 有效范围」，桌子纹丝不动。

## 7. 烧写通道（USB-Serial-JTAG 两个坑）

这块板没有 USB 转串口芯片，USB-C 直连 C3 的 USB-Serial-JTAG（`VID_303A:1001`）。

```bash
# 1) 必须 --no-stub，否则 "Failed to start stub flasher. There was no response."
python -m esptool --chip esp32c3 --port COM4 --no-stub \
    --before default-reset --after hard-reset write-flash 0x0 firmware.bin
```

2. **`--after hard-reset` 会让芯片卡在下载模式出不来**。DTR/RTS 在这块板上没接到 EN，
   "hard reset" 只是复位 USB 外设，下载标志位还在，表现为反复 `rst:0x15 (USB_UART_CHIP_RESET)`
   / `boot:0x7 (DOWNLOAD)` / `waiting for download`。**只有 `--after watchdog-reset` 能真正退出**：

```bash
python -m esptool --chip esp32c3 --port COM4 --no-stub \
    --before no-reset --after watchdog-reset read-mac
```

之后启动模式变为 `boot:0xd (SPI_FAST_FLASH_BOOT)`。真卡死了拔一下 USB 也行（上电复位）。

判断技巧：`rst:0x15` 说明是 USB 外设触发的、软件可控；`0x03 (RTC_SW_SYS_RST)` / `0x0b` 才是真硬件复位。

## 8. 编译环境坑

| 坑 | 现象 | 改法 |
|---|---|---|
| Git Bash 里编译 | `ERROR: MSys/Mingw is not supported`，框架安装失败 | ESP-IDF 见到 `MSYSTEM` 就退出，**必须用系统终端**（PowerShell / cmd） |
| `api.encryption.key` | `must be base64 and 32 bytes long` | 必须 base64 的 32 字节，十六进制不行 |
| 编译很慢 | 首次全量约 3–5 分钟 | 之后增量；改 yaml 会重新生成 C++ 源但只重编部分 |

本机命令：`python -m esphome compile esphome/desk-c3.yaml`（`esphome` 不在 PATH，用 `python -m`）。

## 9. Wi-Fi 配置（不是优化项，是必需项）

```yaml
wifi:
  output_power: 8.5dB        # 满功率 → 反复 AUTH_FAIL（202），不是密码错
  power_save_mode: light     # none 会让射频常醒，同样导致认证失败
```

原因见 `01-硬件接口.md` §7：3V3 余量小，满功率发射瞬间把电压拉塌，WPA3 的 SAE 握手被打断。

## 10. 可调开关（substitutions）

| 键 | 默认 | 作用 |
|---|---|---|
| `desk_min` / `desk_max` | 851 / 1129 | 真实机械行程（**不是**软限位 850/1130） |
| `desk_sit` / `desk_stand` | 851 / 1129 | 一键坐 / 一键站 |
| `boot_sync` | `"true"` | 开机发一帧 `0x07`。设 false 则开机也零流量，代价是 HA 里高度要等第一次动桌子才有值 |
| `post_motion_sync` | `"true"` | 运动后补一帧对齐静态信息。设 false 则彻底零额外流量 |

## 11. 演进记录（不要把旧设计改回去）

| 版本 | 策略 | 结果 |
|---|---|---|
| v1 | 每 900 ms 轮询 `0x07` | 数据最全，但**手控器屏幕永不熄灭** |
| v2 | 运动后补抓 + 零后台 | 屏幕恢复待机，但暴露"首帧丢失 / 定点过冲" |
| **v3（当前）** | v2 + 预热帧 `primed_*` | 静默 + 首帧可靠，定点误差 ≤1 mm |

> 如果哪天觉得"数据刷新不够快"而想加回轮询，请先读 `README.md` 的三条原则。
